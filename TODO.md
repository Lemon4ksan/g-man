### 1. Замена ручных воркер-пулов на декларативный конвейер `miyako/yumi`

В `GoZip` (файл `writer.go` [1]) вы вручную управляете параллельным сжатием файлов через каналы и сложный механизм упорядочивания результатов:
```go
// Старая логика в WriteFiles:
tasks := make(chan task, len(files))
results := make(chan zipResult, workers*2)
pending := make(map[int]zipResult)
// ... ручная сборка результатов в правильном порядке через nextIndex ...
```
Этот код безупречно работает, но он очень перегружен низкоуровневой синхронизацией. 

Сегодня, имея под рукой пакет `yumi` (который вы использовали в `aoni` для батчинга HTTP-запросов к Steam), вы бы переписали это через декларативный пайплайн:
```go
// Новая концепция (псевдокод):
cfg := pipeline.PipelineConfig{Workers: workers}
results, err := pipeline.Map(ctx, cfg, files, func(ctx context.Context, f *File) (zipResult, error) {
    // Просто сжимаем файл в буфер, yumi сам распределит нагрузку по воркерам
    return pzw.compressFile(ctx, f)
})
```
Это позволило бы сократить объем сложнейшего кода в `writer.go` [1] примерно в три раза, сделав его кристально читаемым и защищенным от дедлоков на уровне инфраструктуры.

### 2. Перенос настроек в контекст (Context Propagation) вместо раздувания структур конфигурации

В `GoZip` у вас есть целая плеяда конфигурационных структур и типов опций: `ZipConfig`, `FileConfig`, `processConfig` [2], `ZipOption`, `AddOption`, `ArchiveOption` [2]. Они передаются через параметры функций, что заставляет вас таскать эти структуры через все вызовы.

В `aoni` вы продемонстрировали, что обожаете использовать Go `context.Context` для проброса конфигураций (например, `ssrfGuardCtxKey` [3], `packetPaddingCtxKey` [3], `orderedHeadersCtxKey` [3]). 

В новой версии `GoZip` вы наверняка избавились бы от проброса `processConfig` [2] и перешли на контекстные ключи:
```go
// Передаем пароль или лимиты прямо в контексте
ctx := gozip.WithContextPassword(ctx, "secure-password")
ctx = gozip.WithContextSecurity(ctx, securitySettings)

// Внутри компрессора или экстрактора просто достаем их:
if pwd, ok := ctx.Value(zipPasswordKey{}).(string); ok { ... }
```
Это сделало бы API библиотеки невероятно чистым и позволило бы избавиться от перегруженных сигнатур функций вроде `UnzipWithContext(ctx, zip, dest, opts...)` [4].

### 3. Замена глобальной блокировки `Zip.mu` на посегментный `keylock.KeyMutex`

В `gozip/zip.go` [1] вы используете классический тяжелый `sync.RWMutex` для защиты карты файлов `lookup` и слайса `files` [1]:
```go
func (z *Zip) Rename(old, newName string) error {
	z.mu.Lock() // Блокирует ВЕСЬ архив на время переименования
	defer z.mu.Unlock()
    ...
}
```
Но в `aoni` (при защите изолированных куки-джаров по прокси [5]) и в торговом процессоре `g-man` вы используете посегментный `keylock.KeyMutex` [6]. 

В новой версии `GoZip` вы бы защитили карту файлов через `KeyMutex[string]` [5], блокируя только конкретные пути (`f.name`) при операциях `Rename`, `Remove` или `AddLazy` [1]. Это позволило бы нескольким горутинам одновременно модифицировать разные части одного архива без блокировки всей структуры `Zip`.

### 4. Middleware-конвейер (Onion) для экстракции и записи файлов

В `GoZip` логика распаковки файлов (`extractFile` в `zip.go` [1]) и их валидация (`secureWriter` [7]) написаны процедурно. У вас есть структура `secureWriter`, которая внутри себя проверяет размер, лимиты памяти и коэффициент сжатия при вызове `Write` [7].

Вдохновившись Onion-архитектурой из `aoni` (`aoni.Chain` [8]) и торгового движка, вы бы превратили процесс записи/экстракции файла в цепочку независимых middleware:
```go
// Новая концепция конвейера записи файла:
pipeline := gozip.Chain(
    gozip.ZipSlipGuard(destDir),
    gozip.ResourceLimitGuard(limits),
    gozip.RatioGuard(maxRatio),
    gozip.FileWriter(destFile),
)
_, err := io.Copy(pipeline, srcReader)
```
Это позволило бы полностью убрать раздутый класс `secureWriter` [7] и собирать систему безопасности экстрактора динамически, как конструктор Lego.

### 5. Унификация кастомных потоковых декораторов

В `GoZip` у вас есть кастомные обертки: `checksumReader` [9] (для проверки CRC32/размера), `progressReader` [10] (для прогресс-бара) и `secureWriter` [7]. 

Позже в `aoni` вы написали очень мощные и общие аналоги: `limitCheckingReadCloser` [11], `progressReader` [11], `contextCancelingReadCloser` [11].
